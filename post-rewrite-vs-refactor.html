When to rewrite vs. refactor: a practical guide

May 8, 2026

The rewrite-vs-refactor question comes up in almost every mature codebase. And almost every time, it gets answered emotionally rather than analytically. The engineers who've been fighting the legacy code for three years want to burn it down. The business stakeholders who remember the last rewrite want nothing to do with it.

The truth is somewhere more nuanced.

The case for refactoring

Refactoring should be your default. It's lower risk, it keeps the system running, and it forces you to understand the thing you're changing. When the core problem is code quality — unclear abstractions, missing tests, tangled dependencies — refactoring is almost always the right move. You're correcting the how without changing the what.

A key signal that refactoring is viable: you can still articulate the business logic, even if the code expressing it is a mess. If you can describe what the system should do, you can incrementally change how it does it.

When rewriting makes sense

Rewrites are justified when the problem is structural, not superficial. Specifically:

  • The underlying data model is fundamentally wrong and impossible to migrate incrementally
  • The original design assumptions no longer hold (e.g., went from single-tenant to multi-tenant)
  • The technology is so far from current capabilities that hiring and maintenance costs outweigh the rewrite risk
  • Performance or scalability requirements cannot be met with the current approach

The hybrid path

Most successful "rewrites" we've been part of weren't rewrites at all — they were strangler-fig migrations. New functionality gets built on the new system. Old functionality gets moved over module by module. The legacy system never gets a hard cutover date; it just shrinks until it's gone.

This approach is slower on paper but almost always faster in practice, because it avoids the big-bang integration risk that kills most rewrites.

The question you should be asking

Before framing this as rewrite vs. refactor, ask: what specific problem are we solving? If the answer is "the code is hard to understand," that's a refactor problem. If the answer is "we can't build X without rethinking Y," that's a rewrite conversation. The difference matters.

Architecture decisions made under pressure tend to be regretted later. Take the time to precisely name the problem before picking a solution.
